Lecture 1 + Section 1&2 — OOP Revision (Employee project)

Core definitions (know them word-for-word)

  • Class — the blueprint for an object; one or more objects can be created from it. Object — an instance of a class.
  • Constructor — a special method automatically called when an object is created. Same name as the class, no return type, not inherited, can be overloaded.
  • Method overloading — same method name, different parameter lists, in the same class. Resolved at compile time → static / compile-time polymorphism.
  • Method overriding — a subclass provides its own implementation of a superclass method with the same name, same parameters, same return type. Resolved at run time → runtime polymorphism.
  • Inheritance — a new class extends an existing class and inherits its members. It is an IS-A relationship. Gives reusability, enables overriding, supports abstraction. Java allows single, multilevel and hierarchical inheritance — not multiple class inheritance (ambiguity; allowed only through interfaces).
  • Polymorphism — "many forms": a superclass reference variable can reference a subclass object (Employee e = new SalariedEmployee();). With such a reference you may only call methods defined in Employee, but the overridden version of the actual object executes.
  • Encapsulation — bundle data + methods in a class and hide internals: private fields with getters/setters that validate.
  • Abstraction — hide unnecessary details (coffee machine, ATM). Achieved with abstract classes and interfaces.
  • Interface — a contract: attributes are public static final by default, methods are public abstract by default; a class implements many interfaces and must implement all abstract methods (or be abstract).
  • Abstract class — cannot be instantiated; may mix abstract and concrete methods; contains an abstract method ⇒ the class must be declared abstract; every concrete subclass must implement the abstract methods.
  • toString() exists in every class (from Object) but is only useful once you override it.

The Employee project (the exam's favourite example)

  • Employee (Name, SSN, address; methods getName/setSSN..., and Earning()) → made abstract because Earning's calculation differs per employee type.
  • Subclasses: SalariedEmployee (salary + bonus − deductions), HourlyEmployee (hours × rate), CommissionEmployee (commission on sales), and BasePlusCommissionEmployee which extends CommissionEmployee (two-level hierarchy) and adds a base salary + setBase.
  • Displayable interface: forces every subclass to provide displayAllDetails() and displayEarning() — "the interface is like a contract".
  • Department holds an array of Employees; Main demonstrates Employee e = new SalariedEmployee();

Static members, static block & IIB

  • A static method belongs to the class, can use static data, but cannot use this/super or non-static members directly.
  • A static block runs once at class loading, before main.
  • An Instance Initialization Block (IIB) runs at every new, after the parent constructor (super()) and before the rest of the child constructor.

Lecture 2 + Section 3&4 — SOLID Principles (Robert C. Martin, "Uncle Bob")

SOLID = five design guidelines making code understandable, flexible, maintainable, reusable, less coupled and more cohesive. Guidelines — not patterns, not rules.

How the exam phrases each principle

  • SRP: "one reason to change", "easy to test/understand", "lower coupling", "split saveToDatabase / sendEmail out of the class".
  • OCP: "add a new payment type by creating a new class", "if-else requires modifying the method", "open for extension / closed for modification — don't mix the order up!".
  • LSP: "Square/Rectangle", "Penguin/Bird", "subtype breaks the contract", "throws where the base promises to work".
  • ISP: "large/fat interface forces unused methods", "split into smaller role-specific interfaces".
  • DIP: "depend on abstractions, not concretions", "dependency injected rather than created inside".
Trap: a class that implements an interface but throws UnsupportedOperationException in a method breaks LSP (behavior contract) and signals an ISP design problem (it was forced to implement what it doesn't need). Read the question: asking about the interface being too large → ISP; asking about substitution breaking behavior → LSP.
Lecture 3 + Section 5 — Design Patterns intro & Singleton

Design patterns in general

  • A design pattern = a general, reusable solution to a commonly occurring problem in software design. It is a template to adapt, not code to copy-paste, not an algorithm, and it never replaces testing.
  • Benefits: reusable, maintainable, easy to understand, industry-standard vocabulary, reduces duplication and dependency between components.
  • Prerequisites to learn them: a programming language, OOP concepts, SOLID principles.
  • Three categories:
    • Creational — how objects are created: Singleton, Factory (+ Builder, Prototype).
    • Structural — how classes/objects are composed into larger structures: Adapter, Decorator, Proxy, Facade.
    • Behavioral — how objects communicate/interact: Observer, Command, Strategy, Template, Mediator.

Singleton pattern

  • Restricts a class to one single instance and provides a global access point. Creational pattern.
  • Three implementation steps: private constructor, private static reference to the instance, public static getInstance() that creates the instance if it is null and returns it.
  • Uses: Logger, database connection, configuration manager, caches — any shared resource that must exist once.
public class Company {
    private static Company instance;          // private static reference
    private String name;
    private Company(String name) { this.name = name; }   // private constructor
    public static Company getInstance(String name) {
        if (instance == null) { instance = new Company(name); }
        return instance;
    }
}
// Main: Company a = Company.getInstance("Tech");
//       Company b = Company.getInstance("Other");
//       System.out.println(a == b);   // true  -> same object, same hash code

Exam traps: "public constructor ensures one instance" = False (it must be private). "Create a public static variable to hold the instance" is NOT a proper step — the reference stays private. Singleton is CREATIONAL, not structural. Eager is more thread-safe; Lazy needs synchronization.
Lecture 4 + Section 5 — Factory pattern
  • Factory = creational pattern: create objects without the client knowing the exact class. The client asks the factory for a product by name/type and receives it via the common abstraction.
  • It encapsulates creation logic (hidden from the client), decreases the load on the client, and reduces client–concrete-class coupling.
  • Lecture examples: EnemyFactory (client sends the enemy id → gets a Turtle or Bird), SandwichFactory (Cheese/Chicken Burger), plus ShapeFactory and AnimalFactory in the question bank.
  • Closely related principle: OCP — a new product = a new class + one more branch in the factory; client code unchanged.
interface Shape { void draw(); }
class Circle implements Shape { public void draw(){ System.out.println("Drawing a Circle"); } }

class ShapeFactory {
    public static Shape getShape(String shapeType) {
        if (shapeType.equals("Circle")) return new Circle();
        return null;
    }
}
// Client:  Shape s = ShapeFactory.getShape("Circle");  s.draw();

Factory Method variant (abstract factory class)

public abstract class ShapeFactory {
    public abstract Shape createShape();      // subclass decides the product
    public void renderShape() { createShape().draw(); }
}
public class CircleFactory extends ShapeFactory {
    public Shape createShape() { return new Circle(); }
}
  • Section 5 example: abstract Employee ← Manager/Developer/Intern, built by EmployeeFactory.create(EmployeeType, name); the factory builds the team and the Company Singleton stores it — both patterns working together.
  • Don't use a factory when creation is trivial: it just adds complexity.
Quick-fire exam tips & classic traps
  1. Overloading = same name, different parameters, compile-time. Overriding = same signature in subclass, runtime. "Overloading is runtime polymorphism" = always False.
  2. Inheritance = IS-A; composition = HAS-A / PART-OF.
  3. Abstract class: can have constructors and concrete methods, cannot be instantiated. Interface: contract, no constructor, attributes are public static final; implement many.
  4. Constructors: same name as class, no return type, not inherited, can be overloaded.
  5. SRP question with a class doing X + save to DB + send email → the DB/email parts move out.
  6. OCP: "open for extension, closed for modification" — never the reverse. Violated by if/else type-strings where new types force edits.
  7. LSP: any subclass throwing UnsupportedOperationException instead of honoring the parent's behavior = LSP violation.
  8. ISP: "fat interface", "implements methods it never uses" → split the interface.
  9. DIP: "both depend on abstractions", "injected rather than new-ed inside". Fix = interface + constructor injection.
  10. SOLID letters: Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, Dependency Inversion (Robert C. Martin).
  11. Patterns: 3 categories — Creational (Singleton, Factory), Structural (Adapter, Decorator, Proxy, Facade), Behavioral (Observer, Command, Strategy, Template, Mediator). Observer = GUI event listeners. Mediator = centralizes communication.
  12. Singleton: private constructor + private static instance + public static getInstance(); Lazy = on demand + needs synchronization; Eager = at startup + thread-safe; bad for multiple instances/configurations; complicates unit testing.
  13. Factory: hides creation, promotes loose coupling, supports OCP; client asks for a type and gets the product; factoryMethod() / getShape(type).
  14. Design pattern = reusable solution template, NOT copy-paste code, NOT a testing replacement, NOT always mandatory, NOT only for OOP languages.
